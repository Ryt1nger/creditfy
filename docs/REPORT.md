# Отчёт: как работают сбор данных, анализ и поиск решений

Прототип «Умный кредитный кабинет предпринимателя». Все цифры ниже получены реальным прогоном на демо-данных (`backend/tests`, `docs/test-scenarios.md`). Данные и внешние сервисы синтетические.

## 1. Одной схемой

```
Клиент описывает задачу ─▶ подбор продукта ─▶ заявка (форма + документы)
        │
        ▼
 1. ПОЛНОТА          все поля и документы на месте?  ── нет ─▶ запрос уточнений клиенту (внутри заявки)
        │ да
        ▼
 2. СБОР ДАННЫХ      ЕГРЮЛ/ЕГРИП + БКИ + ФНС «Прозрачный бизнес» (симуляторы)
        ▼
 3. АНАЛИЗ           стоп-факторы → балльный скоринг → кросс-проверки → платёжеспособность (DSCR)
        ▼
 4. ПОИСК РЕШЕНИЯ    запрошенные условия проходят? ── нет ─▶ поиск ближайших подходящих (срок ↑, сумма ↓)
        ▼
 5. МАРШРУТ          автоодобрение │ ручной разбор специалистом │ автоотказ с причиной
        ▼
   предложение ─▶ клиент принимает ─▶ подпись (симуляция) ─▶ выдача, график платежей
```
Каждый шаг пишется в журнал событий. Клиент видит свою часть («Проверяем компанию в реестрах»), банк — полную, включая баллы скоринга.

## 2. Сбор данных

| Откуда | Что берём | Когда | Как проверяем |
|---|---|---|---|
| Клиент, форма | ИНН, цель, сумма, срок, выручка и прибыль за год, оборот по счёту, платежи по кредитам, залог, контакт | при подаче | границы по продукту, суммы ≥ 0, ИНН по контрольной сумме |
| Клиент, документы | выписка, отчётность; по продукту — бизнес-план, счёт; при залоге — документы на залог | при подаче или по запросу | набор определяется продуктом; тип и размер файла; сотрудник принимает/отклоняет |
| ЕГРЮЛ/ЕГРИП (симулятор) | название, форма, ОКВЭД, дата регистрации, руководитель, статус | после полноты | подставляем в заявку, клиент ничего не переписывает |
| БКИ (симулятор) | длина истории, просрочки за 24 мес., действующие кредиты и платежи | после полноты | сверка платежей с заявленными |
| ФНС «Прозрачный бизнес» (симулятор) | налоговый долг, штат, риск-признаки (массовый адрес/руководитель) | после полноты | стоп-фактор и фактор скоринга |
| Система | каждое событие, каждый скоринг, каждое предложение | всегда | журнал не редактируется |

Принципы: клиент вводит данные один раз; всё, что известно из реестров, подтягивается само; недостающее запрашивается точным списком, а не общей фразой «дополните заявку». Каждый источник сохраняется отдельной записью с временем получения, поэтому решение можно воспроизвести.

## 3. Анализ

**3.1 Полнота.** Автоматическая проверка полей и документов продукта. Если чего-то нет, заявка переходит в «Нужны уточнения» и создаётся запрос с перечнем недостающего. После ответа клиента конвейер продолжается сам с того же места.

**3.2 Стоп-факторы (политика банка).** Любой из них даёт автоотказ с причиной: компания ликвидируется; бизнесу меньше 6 месяцев; просрочка больше 90 дней за 24 месяца; налоговый долг больше 100 000 ₽ и больше 5% выручки.

**3.3 Скоринг (прозрачная балльная карта `scorecard-v1`, 0–1000).** Старт 500 баллов, факторы добавляют или снимают баллы.

| Фактор | Диапазоны → баллы |
|---|---|
| Возраст бизнеса | до 12 мес. −40 · 12–36: 0 · 36–60: +30 · свыше 60: +60 |
| Сумма кредита к годовой выручке | <15%: +40 · 15–30%: 0 · 30–50%: −30 · ≥50%: −80 |
| Рентабельность по чистой прибыли | <0: −90 · 0–5%: −20 · 5–15%: +20 · ≥15%: +50 |
| Просрочки в БКИ | нет истории −30 · 0 дн.: +40 · до 30: −50 · до 90: −120 |
| Длина кредитной истории | ≥36 мес. +20 · ≥12: +10 · короче: −10 |
| Налоговая задолженность | нет: +20 · есть: −60 |
| Риск-признаки ФНС | −70 |
| Залог | +50 |
| Оборот по счёту ×12 расходится с выручкой более чем на 35% | −40 и флаг |

Классы: A ≥700 · B ≥620 · C ≥540 · D ≥460 · E ниже (оценка вероятности дефолта 1,5 / 3 / 6 / 11 / 25%). Примеры из прогона: Север-Логистика — **730, класс A** (возраст +60, сумма/выручка +40, рентабельность +50, нет просрочек +40, история +20, нет долга +20); ИП Волков — **540, класс C** (просрочка 12 дн. дала −50).
Каждая запись скоринга хранит версию модели, баллы каждого фактора и флаги, поэтому специалист видит не «оценку», а причины.

**3.4 Скоринг ≠ решение.** Это требование кейса, и оно заложено в структуре. Решение принимает кредитная логика, которая учитывает ещё три вещи: стоп-факторы политики, лимиты продукта и платёжеспособность.

**3.5 Платёжеспособность (DSCR).** Операционный денежный поток в месяц = чистая прибыль за год / 12 × 1,15 (добавка на амортизацию). Из него вычитаются текущие платежи по кредитам, причём берётся **большее** из заявленных клиентом и найденных в БКИ (консервативно). DSCR = свободный поток / ежемесячный платёж по новому кредиту; порог **1,25**.
Расхождения (платежи в БКИ больше заявленных, оборот не сходится с выручкой) превращаются в флаги и не позволяют автоодобрить заявку.

**3.6 Маршрут.** Стоп-фактор или класс E → автоотказ. Класс A или B, без флагов и сумма в автолимите продукта → автоодобрение. Всё остальное → ручной разбор.

## 4. Поиск решений

**4.1 Подбор продукта для клиента.** Описание задачи сопоставляется с признаками четырёх продуктов (оборотные средства, инвестиционный, оборудование и транспорт, овердрафт) и с допустимой суммой. Клиент видит рекомендацию и причину и может выбрать иной продукт. Сейчас это ключевые слова (заглушка), позже модель.

**4.2 Подбор условий вместо отказа.** Если платёж по запросу не проходит по DSCR, система ищет ближайшие подходящие условия: берёт запрошенную сумму и **сначала растягивает срок** (шаг 3 месяца до максимума продукта), и только если не хватает, **снижает сумму** шагами по 5% и снова пробует сроки. Первое подходящее сочетание и есть предложение: клиенту отдаётся минимальное изменение, а сумма сохраняется как можно дольше. Если не проходит даже минимальная сумма продукта, отказ с причиной «недостаточная платёжеспособность».
Пример из прогона: ООО «Пекарня №1» просит 4 000 000 ₽ на 36 мес. (класс B, ставка 17,5%). Свободный поток 147 500 ₽/мес., платёж 143 608 ₽ → DSCR 1,03. Система предлагает **те же 4 000 000 ₽ на 48 мес.**: платёж 116 457 ₽, DSCR 1,27. Клиент видит сравнение «просили / предлагаем» и объяснение.

**4.3 Ставка** = базовая ставка продукта + надбавка за класс (A 0 · B +1,5 · C +3 · D +5 п. п.) − 1 п. п. при залоге. Условия демонстрационные, не реальные тарифы.

**4.4 Ручной разбор.** Специалист получает заявку со сводкой, разложенным скорингом, данными реестров и предложением системы. Он может одобрить как есть, скорректировать условия, отказать с причиной из справочника или запросить данные у клиента (заявка уходит клиенту и возвращается именно специалисту). Решение принимает только андеррайтер; оператор проверяет документы и полноту. Повторное решение невозможно (`409`).

## 5. Где и как работает ИИ

Сейчас **ИИ нет**: есть заглушка, а всё помечено в интерфейсе как «ИИ · заглушка». Решения принимают правила и скоринг, поэтому продукт полностью работоспособен и без ИИ (рекомендация ТЗ). Подготовлены четыре точки подключения (подбор продукта, сводка для специалиста, объяснение статуса клиенту, распознавание документов) и промежуточный класс `DeepSeekProvider`. Модель будет работать локально (open weights), получать только обезличенные признаки и **не принимать кредитных решений**. Подробно: `docs/ai-integration.md`.

## 6. Исследование предметной области

Исследование кабинетное (по тексту кейса и банковской практике), живых интервью не проводилось. Выводы поэтому названы гипотезами, список болей, JTBD и границы MVP — в `docs/research.md`. Главные выводы, на которых построен продукт: пользователь не знает банковских терминов, поэтому продукт подбирается по описанию задачи; пользователь не должен вводить повторно то, что есть в реестрах; статус должен объясняться человеческим языком вместе со следующим шагом; отказ без объяснения теряет клиента, поэтому вместо отказа ищется встречное предложение.

## 7. Что проверено и чего нет

| Проверено | Как |
|---|---|
| Сквозной путь: заявка → проверки → скоринг → решение → подпись → выдача | `pytest`: 10 сценариев из 10 проходят |
| Автоотказ по стоп-факторам, встречное предложение, ручной разбор, цикл уточнений | те же тесты |
| Права доступа (чужая заявка, роль), валидация входа, лимиты файлов | `test_security` |
| Цифры демо-экранов совпадают с бэкендом (ИНН, платёж, встречные условия) | `frontend/src/lib/parity.test.ts` |
| Весь путь в реальном браузере против живого API: вход → мастер → отправка → одобрение → подпись → выдача → кабинет банка, ошибок в консоли и 4xx/5xx нет | прогон Playwright (SQLite, без Docker) |

| Не проверено | Причина |
|---|---|
| Запуск в Docker | в среде разработки нет демона Docker; файлы написаны, нужен прогон `docker compose up --build` |
| Нагрузка, безопасность за пределами базовых мер | вне объёма прототипа |
| Модель скоринга на реальных данных | калибровка весов не выполнялась: веса экспертные и объяснимые, не обученные |
